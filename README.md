# Dishcovery serialization benchmark: reproducibility package

Data and analysis code for the paper *Comparative Analysis of JSON,
MessagePack, and Protocol Buffers on Performance Efficiency and Resource
Utilization in AI-Powered Mobile E-Applications* (Kevin Nathanael, Michelle
Daphne Langitan, Anderies; BINUS University, 2026).

Every number in the paper's results tables can be recomputed from the raw run
data in this package with one script.

## What was measured

The same 250 recipe payloads were decoded by a React Native app on an Android
phone in three encodings: JSON, MessagePack and Protocol Buffers. For each
payload and format the app recorded:

- **Payload size**: bytes on the wire.
- **Deserialization time**: wall-clock time of the decode call, from the
  received bytes to a decoded object, in milliseconds.
- **Heap allocation**: bytes allocated by the JavaScript engine during the
  decode, read from Hermes' `js_totalAllocatedBytes` counter with a constant
  208 B measurement offset subtracted.

## Device and build

An Infinix X6871 on Android 15 (API 35), running a release build of the
Dishcovery app: React Native 0.79.2, Hermes with precompiled bytecode, Expo
SDK 53, `@msgpack/msgpack` 3.1.3 and `protobufjs` 8.8.0. Full details,
including the app commit and the APK hash, are in
[environment.md](environment.md).

## Dataset

250 payloads with one fixed shape (`dataset/recipe.proto`):

- 100 real recipes from the Spoonacular API, all in the low tier.
- 150 recipes generated by a language model, 50 in each tier, so the medium
  and high tiers could be filled.

Tiers are set by the UTF-8 byte length of the JSON encoding: low < 7,500
bytes, medium 7,500 to 14,000, high > 14,000.

The raw Spoonacular payloads are not included until their licence terms have
been checked. Their IDs, tiers and sizes are included, with a script to
re-fetch them. See [dataset/DATASET.md](dataset/DATASET.md).

## Run protocol

Each run:

1. Pre-warms the engine with 200 decodes per format.
2. Decodes a fixed sentinel payload 150 times per format, as the start
   sentinel.
3. For each of the 250 payloads x 3 formats, does 10 warm-up decodes, which
   are discarded, and then 30 measured decodes. That is 22,500 measured rows
   per run. The sentinel is repeated halfway through and at the end.

A run is valid only if the sentinel's mean decode time drifts by less than 5%
between start and end, in every format. Runs are at least 10 minutes apart.

The pre-warm and warm-up sizes were checked against warm-up profiles measured
on the same build (see [runs/RUNS.md](runs/RUNS.md)):

- **Engine warm-up:** cold-start profiles show the engine settles within 20
  decodes (140 under a stricter rule), so a pre-warm of 200 covers both.
- **Per-payload warm-up:** a per-payload profile shows the first-decode
  transient settles within 10 decodes, matching the warm-up of 10.

The paper pools **three runs from one day, 2026-10-15**. Six other runs on the
same build are kept:

- Four clean **replication** runs, which were not pooled because only three
  runs were planned and two of them are from another day.
- Three **excluded** runs, each with a measured problem.

[runs/RUNS.md](runs/RUNS.md) lists every run with its drift, its gap to the
previous run and the previous profile, and the reason for its status.

**About the cooldown.** The 10-minute rule applies between benchmark runs. A
cold-start profile (about 25 s, one payload) is not treated as a run, so a run
that starts a few seconds after a profile is not in breach. The start
sentinels show no carry-over in any run.

One final run is an exception to the rule as written. Run
2026-10-15T03-32-12-987Z started 377 s after the previous run (an excluded run)
finished. The app's cooldown check did not flag this. RUNS.md records it as it
happened.

## Reproducing the tables

Python 3.12 or newer is required, because scipy 1.18.1 needs it. From the
package root:

```
python -m venv .venv && .venv/bin/pip install -r requirements.txt     # Windows: .venv\Scripts\pip
.venv/bin/python analysis/analyze.py runs/final analysis/output        # Windows: .venv\Scripts\python
diff --strip-trailing-cr analysis/output/report.md analysis/reference_output/report.md
```

The script reads the three CSVs in `runs/final/*/`, checks their integrity and
writes every table to `analysis/output/`. `analysis/reference_output/` is the
output the paper was written from, kept unchanged so a fresh run can be
compared against it.

On Windows (Python 3.13.16) the regenerated `report.md` matches the reference
line for line. Two kinds of byte difference are expected:

- **Line endings.** Python writes CRLF on Windows, and the reference has LF.
  Compare with `--strip-trailing-cr`.
- **Floating-point noise in three CSVs.** `anova.csv`, `crossover.csv` and
  `paired_protobuf_vs_msgpack.csv` can differ in the 16th or 17th significant
  digit, for example `0.920138920779753` against `0.9201389207797526`. These
  digits are far below anything printed in the report or the paper.

The engine warm-up figures can be checked with Node.js 22.6 or newer and no
packages:

```
node --experimental-strip-types analysis/warmup/verify_warmup.ts
```

## Contents

```
dataset/          payload definitions, sizes, generated payloads, Spoonacular IDs
runs/final/       the three pooled runs: CSV + aggregate.json each
runs/replication/ clean runs not pooled (aggregate.json only)
runs/excluded/    excluded runs (aggregate.json + REASON.md)
runs/profiles/    cold-start profiles and per-payload profile screenshots
runs/RUNS.md      every run, its timing, drift and status
analysis/         analyze.py, its output, the reference output, warm-up check
CHECKSUMS.sha256  SHA-256 of every file in the package
```

All run data (CSV and JSON) is byte-identical to the files exported from the
app. Check it with `sha256sum -c CHECKSUMS.sha256`.

## Known limitations

- **One device.** Every measurement comes from a single Infinix X6871. Absolute
  times will differ on other hardware, and the ranking between formats may
  shift on devices with a different CPU or memory system.
- **One implementation per format.** Each format was measured through one
  library in one JavaScript engine: Hermes `JSON.parse`, `@msgpack/msgpack`,
  and `protobufjs` static code. The results describe these implementations,
  not the formats in general.
- **Allocation, not peak memory.** The Hermes counter measures the volume of
  memory allocated during a decode. It does not measure peak or resident
  memory, and it does not count memory freed during the decode.
- **Generated payloads.** The medium and high tiers consist only of generated
  recipes, so tier and provenance are confounded above the low tier. The
  low-tier provenance control in the report compares the two sources where
  both exist.
- **Spoonacular payloads withheld.** Until the licence check is done, the 100
  real payloads cannot be decoded from this package. Their re-fetched content
  may differ from what was measured.
- **Per-payload warm-up profile.** Only screenshots of it exist, so it cannot
  be recomputed.
- **App warm-up verdict.** The app read only one cold profile at the start of
  each run, so every `aggregate.json` reports its warm-up verdict as
  "unverified". The verification in the paper is computed from the profile
  files instead.
