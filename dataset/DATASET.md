# Dataset

250 recipe payloads, each served to the app in three encodings: JSON,
MessagePack and Protocol Buffers.

| Source | Low | Medium | High | Total |
|---|---|---|---|---|
| Spoonacular API (real recipes) | 100 | 0 | 0 | 100 |
| Generated by a language model | 50 | 50 | 50 | 150 |
| **Total** | 150 | 50 | 50 | 250 |

## What a payload is

Every payload has the same shape, defined in `recipe.proto`: title, image URL,
ready time, servings, summary, a list of nutrients, a list of ingredients and a
list of instruction sets with their steps. The proxy that served the benchmark
reduced each source document to these fields and then encoded the result three
times: as JSON text, as MessagePack (`@msgpack/msgpack` 3.1.3) and as Protocol
Buffers (`protobufjs` 8.8.0, generated from `recipe.proto`). The three
encodings of a payload carry the same values; only the wire format differs.

`recipe.proto` is a byte-identical copy of `shared/proto/recipe.proto` from the
app at the build commit (see `environment.md`).

## Tiers

A payload's tier is set by the UTF-8 byte length of its JSON encoding:

| Tier | JSON bytes |
|---|---|
| low | < 7,500 |
| medium | 7,500 to 14,000 |
| high | > 14,000 |

The classifier in the app also looks at nesting depth (low up to 6, medium up
to 8) and takes the higher of the two tiers, but no payload in this dataset is
deeper than 5 levels, so every tier here is the size tier.

## Payload sizes

`payload_sizes.csv` has one row per payload: `payloadId`, `source`, `tier`, and
the wire size in bytes of each encoding (`json_bytes`, `msgpack_bytes`,
`protobuf_bytes`). It is the file `analysis/analyze.py` writes to
`analysis/output/payload_sizes.csv`, built from the `wireBytes` column of the
final runs. The wire size of every payload was the same in all three runs.

## Spoonacular payloads (`spoonacular/`)

- Harvested on 2026-09-09 between 02:10:51 and 02:12:03 UTC from
  `api.spoonacular.com`, endpoint `/recipes/{id}/information` with
  `includeNutrition=true`.
- Candidate IDs came from `complexSearch` queries for pasta, chicken, salad,
  soup, curry, dessert, breakfast and seafood. 149 candidate IDs were seen;
  the harvest stopped at its target of 100 verified recipes, with no failed
  verifications.
- All 100 fall in the low tier (3,754 to 7,108 JSON bytes). Real API recipes
  are not large enough to fill the medium and high tiers, which is why the
  generated stratum exists.

**The raw Spoonacular payloads are withheld pending a licence check.** They
are not in this package until Spoonacular's terms on redistribution have been
checked. What is included:

- `spoonacular/recipe_ids.csv`: recipe ID, tier and JSON byte length for all
  100 recipes. These match the harvest record and the run data exactly.
- `spoonacular/refetch.py`: downloads the same 100 recipes again by ID. It
  reads the API key from the `SPOONACULAR_API_KEY` environment variable and
  never writes it anywhere. Spoonacular content can change, so a re-fetched
  recipe is not guaranteed to match the bytes used in the study. The byte
  lengths in `recipe_ids.csv` are the reduced JSON the benchmark decoded, not
  the raw API response.

## Generated payloads (`generated/`)

150 synthetic recipes. **They are not real recipe data** and should not be
cited as such. They were produced so that the medium and high tiers could be
filled with documents of the same shape as the Spoonacular ones.

- Model: Gemini 3.6 Flash (`gemini-3.6-flash`, version `3.6-flash-07-2026`),
  temperature 1, JSON response mode with a response schema.
- Generated in batches between 2026-09-12 and 2026-09-22 UTC (8 sessions, 47
  requests). The manifest was finalised on 2026-09-22 10:06 UTC.
- Prompts: `generated/prompts/`. These are byte-identical copies, and their
  SHA-256 hashes match the ones recorded in `generated/manifest.json`
  (`promptArtifacts`).
- Each candidate was checked before it was accepted:
  - **Tier band:** its JSON byte length had to fall in the target band for its
    tier.
  - **Text density:** characters per instruction step between 67.4 and 150. The
    floor is the 10th percentile of the harvested Spoonacular recipes.
  - **Value sanity:** for example, percent of daily needs at most 1,000.
  - **Near-duplicates:** rejected at Jaccard similarity of 0.6 or more on word
    3-gram shingles of the title, ingredient names and steps.
  - The full rules and their history are in `generated/manifest.json`
    (`validation`, `nearDuplicate`, `targetBands`).
- Accepted: 50 low, 84 medium, 50 high. Rejected: 1 medium (value sanity), and
  16 high (14 tier-band misses, 1 text density, 1 value sanity).
- Selection: low and high used every accepted recipe. Medium had 84 accepted,
  so 50 were drawn with a seeded shuffle (mulberry32, seed 20260913,
  Fisher-Yates over the accepted IDs sorted ascending, first 50). The selected
  IDs are listed in `generated/manifest.json` under `selection.perTier`.
- JSON bytes of the selected payloads: low 4,577 to 5,103; medium 9,235 to
  11,358; high 15,245 to 19,403.

`generated/<id>.json` holds the 150 selected payloads, byte-identical to the
files the proxy served. IDs run from 9000001 upward. `generated/manifest.json`
is the full generation record. It also lists the 34 accepted medium recipes
that were not selected, and every rejected attempt. Those payloads, the raw
model responses, and an earlier single-document generation run that was
quarantined (a different procedure, not used) are in the app repository, not
in this package.

## Validation against the run data

- Every payload ID, source, tier and JSON byte length in `payload_sizes.csv`
  matches `spoonacular/recipe_ids.csv` and `generated/manifest.json`.
- In each final run the JSON wire size equals the canonical byte length for
  every payload, and every payload x format had the same wire size in all
  three runs. Both checks are in the integrity section of
  `analysis/output/report.md`.
